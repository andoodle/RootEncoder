The reason this was worth doing

Upstream fixed our bug — wrongly

›

The suspicion going in was that upstream's getFullPath work might make the GPX SrtClient.kt patch redundant. It did the opposite: upstream found the same SRT streamid bug and fixed it in a way that drops the Millicast publishing token.

// upstream — falls back to getFullPath() only when the path is EMPTY
urlParser.getQuery("streamid") ?: urlParser.path.ifEmpty {
  if (urlParser.query == null) urlParser.getFullPath() else ""
}

A Millicast SRT URL is srt://srt-<cluster>.millicast.com:10000/<name>?t=<token>&latency=<ms>. The path is <name> — never empty — so upstream's expression returns the name alone and the ingest rejects it. Ours keeps the query attached.

Both sides changed the same line, so it was the merge's one conflict. The full reasoning now lives as a comment at that line, so the next sync doesn't quietly undo it. That comment is the durable half of this finding.

Source fallback — unreachable

ec949a59c lives in StreamBase.changeVideoSource/changeAudioSource. gpxstream-app calls neither — zero call sites across the app. S3 decision 3 has it driving Camera2ApiManager directly. Also: the change is a rollback on failure, not a silent substitution, so the title misleads.

UrlParser — output-identical

Proven, not assumed: a test asserting parser output for the real Millicast SRT, RTMP and WHIP endpoints, run against both the old and new UrlParser.kt in the same tree. Same answers. The rewrite is marginally more robust — the query is split off before URI parsing.

Autofocus — inert

c1a5bad0e lands in Camera2ApiManager.kt beside R23 and R25, but inside enableAutoFocus/disableAutoFocus. Nothing in the fork calls them internally and the app never calls them. Auto-merged; the three coexist.

Buffer pool — the one real risk

Touches every encoded frame on both the stream and record path. Our R12 reports write failures through the listener rather than throwing, so upstream's new release-in-finally is undisturbed. But a buffer recycled in-flight corrupts media rather than crashing — hence the bench item.

Method & gotchas

›

The merge was run for real before touching the branch — on a detached-HEAD throwaway worktree, so nothing could land on gpx-2.8 by accident.

git worktree add --detach .claude/worktrees/probe gpx-2.8
cp local.properties .claude/worktrees/probe/
git -C .claude/worktrees/probe merge pedro/master
# resolve, build, test, then delete the worktree entirely
  • Faster first read: git merge-tree --write-tree --name-only <a> <b> gives the conflict list with no worktree at all. Reach for the probe only once a build is needed.
  • The A/B swap: restoring one file from HEAD~1 into an otherwise-merged tree and re-running the same test isolates whether a rewrite changed behaviour. Works for any self-contained file.
  • Windows: git worktree remove --force failed with Filename too long on deep Gradle dirs. It still deregistered the worktree; clean up with cmd /c rmdir /s /q <path> then git worktree prune.
Answered, no code written

Focus & exposure sidebar

›

Andy asked whether autofocus, tap-to-focus and exposure are worth having on the built-in or USB camera. Set aside as app-side work — recorded here so it isn't re-derived.

  • Focus ≠ exposure. The fork's tapToFocus sets CONTROL_AF_REGIONS only, never CONTROL_AE_REGIONS. A tap sharpens the subject and leaves brightness alone.
  • Capture card: no lens, and the picture was already exposed upstream of the phone. tapToFocus self-bails on CONTROL_MAX_REGIONS_AF == 0.
  • USB camera: genuinely unknown — wants a bench probe.
  • The probe is app-side and needs no camera open. GpxCameraSource already calls getCameraCharacteristics. Read CONTROL_AF_AVAILABLE_MODES, LENS_INFO_MINIMUM_FOCUS_DISTANCE, CONTROL_MAX_REGIONS_AF, CONTROL_MAX_REGIONS_AE, CONTROL_AE_AVAILABLE_MODES, CONTROL_AE_LOCK_AVAILABLE, CONTROL_AE_COMPENSATION_RANGE.
  • The only possible fork change (future R27): make a tap set the exposure region too, guarded on CONTROL_MAX_REGIONS_AE > 0. ~4 lines.
  • Caution: tapToFocus calls stopRepeating() — frames halt and restart. Possibly a visible hitch live.
