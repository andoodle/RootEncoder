Root cause

One Port Commit, Three Bugs

›

All three bugs trace to 2fefe4c0e — porting patches from a separate "alexsafe" fork (pedro 2.6.7 base) onto this fork's pedro 2.7.5 base. Classic copy-paste-during-port pattern: a constant copied instead of changed, a line duplicated into a sibling function and left commented out, debug scaffolding never stripped.

  • CodecUtil.java:420 — isVbrSupported checked BITRATE_MODE_CBR twice instead of _VBR. Log-only, zero downstream impact — confirmed upstream never had this code at all, so no PR, local fix only.
  • StreamBase.kt — two prepareVideo overloads, one had VBR-forcing active, the sibling had the identical line commented out. Fixed by a concurrent gpxnative-ai session via a new forceRecordVbr param, found already applied mid-session.
  • OpenGlView.kt — takePhoto(width, height, cb) was a stub that dropped the size params. Confirmed unreachable from the app (only GlStreamInterface, which was already correct, is used) — fixed anyway for library correctness.
Gotcha

Shared Checkout, Live Concurrent Edits

›

gpxnative-ai's Gradle composite build sets rootencoder.local=true / rootencoder.dir=D:/Development/RootEncoder — pointing straight at this checkout. A session working that app's spec edits this repo's source directly, uncommitted, possibly while another session is also working here.

Symptom hit this session: a Grep on StreamBase.kt showed the old buggy VBR-forcing code; ~15 tool calls later (after a detour into gpxnative-ai to read its spec), the same file showed the fix already applied — with no edit from this session in between. Confirmed via git diff it matched the concurrent session's spec exactly rather than being a surprise regression.

Takeaway: in this repo, "clean git status at session start" is a snapshot, not a guarantee that holds mid-session. Re-check before assuming a file's prior-read state still holds.
